# Synthetic filesystem-boundary fuzzing

Rizzer includes a deliberately narrow C fixture for testing how a service
handles an **untrusted opaque identifier** before constructing a destination.
This was motivated by published research on client-provided metadata reaching
filesystem operations in remote-control software. It does not import XWorm,
contact a command-and-control server, attempt code execution, or touch any real
recovery folder.

The fixture is in fixtures/path_boundary.c. It implements two pure functions:

- rz_validate_component(data, length): only accept 1–64 bytes forming one
  ASCII component, using letters, digits, underscore, hyphen, and optional
  *interior* dots; no ".." subsequence
- rz_build_destination(data, length, buffer, capacity): if accepted, form
  exactly /synthetic/recovery/ID/record.bin in memory; otherwise return
  failure without modifying the destination buffer

It rejects traversal tokens, both slash styles, rooted and drive-style paths,
colon/ADS syntax, control characters, Unicode bytes, percent-encoding,
trailing dots or spaces, and DOS device basenames (CON, PRN, AUX, NUL,
COM0–9, LPT0–9, including name extensions). This is intentionally more
restrictive than a generic Windows filename policy.

## Run it offline

From the Rizzer repository root (Linux; Python 3.11+; Clang and Clang++):

    python3 -m unittest -v test_path_boundary

To run a standalone coverage-guided campaign:

    python3 run.py \
      --source fixtures/path_boundary.c \
      --corpus fixtures/path-boundary-corpus \
      --out /tmp/rizzer-path-boundary-unique \
      --runs 192 --seed 27013 --seconds 20

The output directory must be absent before running. Its evidence.json,
summary.json and journal.jsonl use the existing native fuzz engine's
versioned evidence structure. It reports coverage and candidate failures,
not exploitability or a validated vulnerability.

## Two independent test paths

1. Python compiles the standalone C fixture as a shared library, calls both
   pure entry points through ctypes, and checks accepted and rejected inputs,
   capacity failures and 512 deterministically generated byte sequences.
2. The native coverage-guided engine compiles the same C source with ASan,
   UBSan and trace-pc-guard, then replays a small corpus and deterministic
   mutations. Property violations would trigger a candidate failure via
   __builtin_trap(), never an outside-directory file write.

The Python suite uses ntpath only to illustrate how a **naive virtual path
join** can escape an intended folder. No path is opened, created or deleted
by the fixture.

## Critical limitations

This is a **single-component policy**, not a comprehensive filesystem API
and not a verified Windows Path.Combine equivalent. Windows has additional
path parsing and device-namespace behavior. Windows real-path security
depends on reparse points, symlinks, junctions, directory handles, race
conditions, filesystem permissions, and platform APIs. None of those are
exercised by this in-memory C fixture.

An identifier being valid does not establish that the parent directory is
trusted or non-symlinked. In production, admission checks are only one layer:
use directory-handle-relative operations, safe file creation and appropriate
privilege and reparse-point controls for the target OS, validated separately.

No network access, malware specimens, persistence, payloads, privilege
changes, or C2 capability is provided. The fixture and test corpus are
synthetic Apache-2.0 examples only.
